## CONFIRMED

- **State writes can escape the project through a symlinked `.ude` directory.** [01-04-PLAN.md:145](<.planning/phases/01-sync-engine-state-hermeticity/01-04-PLAN.md:145>) directs `stage_to_dir` to `create_dir_all(.ude)` then `NamedTempFile::new_in(.ude)` without validation. This directly violates the locked instruction to run `validate_safe_write_target` on every staged target ([01-CONTEXT.md:91](<.planning/phases/01-sync-engine-state-hermeticity/01-CONTEXT.md:91>)). The existing validator would reject a symlinked parent ([src/sync/mod.rs:1081](<src/sync/mod.rs:1081>)-[1100](<src/sync/mod.rs:1100>)), but the plan bypasses it. Reproduction: make `project/.ude` a symlink to an attacker-controlled directory; any state save writes there. None of the planned state tests plants that parent symlink.

- **`resolve` commits the resolution before it knows it can remove the sidecar.** [01-10-PLAN.md:125](<.planning/phases/01-sync-engine-state-hermeticity/01-10-PLAN.md:125>) explicitly says: mutate/clear the conflict, “Save state (atomic). Then remove the sidecar.” A symlinked or non-regular `<file>.conflict` therefore returns an error only after the conflict record is gone. That contradicts both D-09’s required paired outcome—record cleared **and** sidecar removed ([01-CONTEXT.md:44](<.planning/phases/01-sync-engine-state-hermeticity/01-CONTEXT.md:44>))—and the plan’s own must-have ([01-10-PLAN.md:26](<.planning/phases/01-sync-engine-state-hermeticity/01-10-PLAN.md:26>)). Reproduction: create a valid conflict, replace its sidecar with a symlink, run `ude sync resolve`; it fails but has already authorized a subsequent push. No negative control tests this failed-sidecar-removal path.

- **The plans have no project-state concurrency control; `resolve` can race a pull and resurrect a resolved conflict.** [01-10-PLAN.md:127](<.planning/phases/01-sync-engine-state-hermeticity/01-10-PLAN.md:127>) deliberately dispatches `resolve` with “no remote lock.” The only lock in the current code protects the remote cache, not the project’s `.ude/state.json` or working tree ([src/sync/mod.rs:416](<src/sync/mod.rs:416>)-[431](<src/sync/mod.rs:431>)). Meanwhile pull stages an old state and commits it after file writes ([01-06-PLAN.md:113](<.planning/phases/01-sync-engine-state-hermeticity/01-06-PLAN.md:113>)). Reproduction: pause pull after staging its conflict record; run resolve; resume pull. Pull commits its stale state/sidecar, undoing the resolve. “Single user” does not make two CLI processes impossible, especially with agents/scripts.

- **The v1→v2 migration does not meet the stated one-way migration contract for read-only commands.** D-07 says existing state files “get migrated” on first load ([01-CONTEXT.md:37](<.planning/phases/01-sync-engine-state-hermeticity/01-CONTEXT.md:37>)). The plan instead makes migration in-memory only and persists it “on the next save” ([01-05-PLAN.md:29](<.planning/phases/01-sync-engine-state-hermeticity/01-05-PLAN.md:29>), [157](<.planning/phases/01-sync-engine-state-hermeticity/01-05-PLAN.md:157>)). A user repeatedly running only `ude sync status` remains on disk at v1 indefinitely. The tests prove a later save produces v2, not that first load durably migrates the ledger.

- **“A clean pull never leaves a `.conflict` file” is tested vacuously.** The requirement is absolute ([01-09-PLAN.md:32](<.planning/phases/01-sync-engine-state-hermeticity/01-09-PLAN.md:32>), echoing the remediation negative control [docs/REMEDIATION_PLAN.md:78](<docs/REMEDIATION_PLAN.md:78>)). Its “negative control” starts a second project with no conflict and no sidecar ([01-09-PLAN.md:194](<.planning/phases/01-sync-engine-state-hermeticity/01-09-PLAN.md:194>)). A pull implementation that never removes stale artifacts passes that test. The plans also never decide whether an orphaned user-created `*.conflict` is safe to delete, so the stated criterion is either false or demands destructive scope not authorized by D-09.

## SUSPECTED

- **PR-mode’s claimed stale-base behavior is untested and likely only deferred to GitHub’s UI.** [01-11-PLAN.md:30](<.planning/phases/01-sync-engine-state-hermeticity/01-11-PLAN.md:30>) claims a moved base “surfaces as a PR conflict,” but its tests cover only direct-push races and pre-receive rejection ([01-11-PLAN.md:251](<.planning/phases/01-sync-engine-state-hermeticity/01-11-PLAN.md:251>)-[255](<.planning/phases/01-sync-engine-state-hermeticity/01-11-PLAN.md:255>)). Current PR mode merely pushes a fresh branch then invokes `gh pr create` ([src/sync/mod.rs:933](<src/sync/mod.rs:933>)-[1009](<src/sync/mod.rs:1009>)); it does not inspect PR mergeability. Confirm with a GitHub-backed test where base advances after fetch and the PR is unmergeable.

## SPECULATION

- **The detached-reader escape path may be operationally noisy under repeated hostile helpers.** [01-01-PLAN.md:140](<.planning/phases/01-sync-engine-state-hermeticity/01-01-PLAN.md:140>)-[142](<.planning/phases/01-sync-engine-state-hermeticity/01-01-PLAN.md:142>) deliberately detaches readers when descendants escape the process group. This preserves the call deadline, but no test measures repeated invocations, thread/resource accumulation in an embedding process, or escaped helper cleanup. It needs a bounded-repeat probe to establish whether it is merely a CLI-lifetime limitation or a denial-of-service vector.

I would not let an automated executor run these plans as written. The resolver can durably clear a conflict while failing to remove its safety artifact; state writes bypass the mandated symlink barrier; and there is no serialization between the two commands that mutate the same ledger. Those are design defects, not implementation details an executor can safely infer around.
