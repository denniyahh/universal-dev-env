Close review WR-600 (02-REVIEW.md, committed c5e170e) as the operator decided on 2026-11-04 (STATE.md): fix it, do not widen NOT-14. The publication gate's in-process tree walk (verified_tree_listing and push_tree_entries since 02-24, listing_diff since 02-25) has no limit on the records it lists and no overall deadline. A commit whose subtrees repeat lists 2^d paths from d + 3 tree objects: the review measured d = 20 at a 338 MB listing, 33 s and 1.14 GB peak in a debug build. The `git ls-tree` and `git diff-tree` runs these functions replaced were each bounded by the local timeout (SYNC-03).

This plan caps the records and the listing bytes one gate call lists (one budget shared by every listing of the call; bytes because a record holds its full path and entry names can be long) and puts one deadline, the local time limit, on the whole walk, listing_diff included. Past either bound the gate fails closed with a fixed text that names the bound. It also corrects T-02-102 (02-24), which recorded the walk as mitigated because each read is bounded: the cost is spent outside the reads (T-02-110 below).

The change loop after listing_diff stays outside the deadline, as the orchestrator decided on 2026-11-04 (the operator delegated the choice): the existing repeated-path check moves before that loop instead, so a commit that repeats an allowlisted path is refused before any repeat's blob is read, and with unique paths the loop reads at most one blob per allowlisted path (T-02-115).

Purpose: the gate's own work is bounded again, so a hook in the cache checkout cannot make `ude sync push` exhaust memory or run without a deadline, and no legitimate push is refused (measured).

Output: production code in src/sync/mod.rs (MAX_LISTING_RECORDS, ListingBudget, listing_budget, DiffDefect, ListingDefect::TooLarge and ::PastDeadline, four cfg(test) seams; both routes and listing_diff bounded; the repeated-path check before the change loop, with five tests updated to its text); RED rows and the tests that pass on first run; measurements; the todo's `## Added by plan 02-27`. ## Decisions and assumptions recorded here

- **The record limit is 1 << 18 = 262,144 records per gate call (planner).**
  - This repository's whole tree lists 286 records (56 trees) at e9165f0, so one push's two listings use about 570: the limit is over 400 times that. The project's own test fixtures list far fewer, apart from the under-limit test this plan adds by construction.
  - The deadline already caps a legitimate walk at the trees it can read in 30 s: each tree costs three local-tier git runs, each at least one 10 ms poll, so at most about 1000 distinct trees (reasoned; Task 3 measures the per-tree cost). With any common fan-out that is far fewer records than 2^18, so the record limit does not decide for a legitimate repository.
  - From the review's table, a debug build lists about 110,000 to 170,000 records a second and holds about 370 bytes a record at gate level, so a gate call at the limit should cost about 2 s and about 100 MB. That is extrapolated, not measured; Task 3 measures it against bounds. 1 << 20, the review's example, would cost about four times the memory for headroom no template repository needs.
- **The byte limit is 1 << 26 = 64 MiB of listing bytes per gate call (orchestrator ruling 2026-11-04, plan-checker iteration 1).** A record limit alone does not bound memory: each record holds its full path, and git does not limit an entry name's length (the checker made 64 KiB names with `git mktree`). This repository's whole listing is 29 457 bytes at e9165f0, so 64 MiB is over 2000 times one push's two listings; it equals 2^18 records at 256 bytes a record, so the two limits are of one size. Charged with the records, before the entries are pushed. count_empty_directories is made linear (parent paths only) so every consumer is linear in the bytes this limit bounds. Two planner runs for this revision were stopped by a safety filter before editing; the orchestrator wrote it by hand and logged that in ~/.config/agents/gsd-manual-fix-incidents.md.
- **One budget per gate call, shared by its listings (planner).** A per-listing limit would let the committed route hold twice the limit across its two listings and listing_diff's copies; one shared budget bounds the call's memory by one number. The commit's listing comes first (02-25's order), so it draws first.
- **The budget is taken before a tree's entries are pushed, not as records are written (planner).** Then the listing and the pending stack together never pass the limit, including a single tree with very many entries.
- **The deadline is self.limits.local, LOCAL_TIMEOUT, from the start of the walk (planner, as the orchestrator asked).** The work the walk replaced was `git ls-tree` and `git diff-tree`, each bounded by LOCAL_TIMEOUT under SYNC-03. One deadline of the same tier over the whole walk keeps the gate's in-process work within one local-tier bound. Test engines keep the field's derivation: test_listing_budget_deadline_follows_the_local_time_limit pins it through with_limits.
- **Where the deadline is checked (planner).** First thing in push_tree_entries, so before the root and every tree record the walk pops, and at each pass of listing_diff's two loops. A blob record between two checks costs no read, and one tree's entries are bounded by the record limit. listing_diff's sort runs on at most the limit's records and is not interrupted.
- **Separate seams, not with_limits (planner).** with_limits shortens every git read too, and a timed-out read gives the read-failure text; then a test could not tell the deadline from a slow read. The time seam shortens only the walk, which is the deadline rows' negative control.
- **Test-only seams with a dead-code expectation in the RED commits (planner).** The seam must exist for the RED rows to compile; nothing reads it before the fix, so the field carries `#[expect(dead_code)]` until GREEN removes it. This matches 02-24's RED commits, which added production seam code under cfg(test).
- **DiffDefect is its own enum (planner).** listing_diff can be unparseable or past the deadline but never over the record limit; a separate enum keeps validate_committed_tree's match exhaustive without a catch-all arm.
- **Refusal texts (planner's discretion).** Two fixed texts, each with a route phrase: `the tree of the commit to publish`, `the tree of the fetched head`, `the fetched head's tree` (empty-status route), `the changes of the commit to publish`. No number is printed, so a test-shortened bound prints the same text as production.
- **The change loop: the repeated-path check moves before it (orchestrator decision 2026-11-04, the operator delegated it).** The loop stays outside the deadline, so a legitimate push is not limited to the changes it can read in 30 s. Moving the check, unchanged, ahead of the loop leaves the loop at most one blob read per allowlisted path. It goes right after the fetched head's listing, before listing_diff, the placement measured at plan time (five tests change their expected refusal and no other test changes; Task 2's table). The proof is a read counter in a cfg(test) seam, not the refusal text: the text was already `repeats a path` before the fix, only after one read per repeat.
- **The tree ceiling (operator 2026-11-04: template repositories are far below 1000 directories; keep the deadline).** The deadline refuses a legitimate repository whose walk needs more than LOCAL_TIMEOUT. Task 3 records the measured per-tree cost and the implied ceiling; this repository is far below it.
