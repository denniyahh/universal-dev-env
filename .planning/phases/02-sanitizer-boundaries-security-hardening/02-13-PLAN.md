<objective>
Close gaps 1, 2, 4 and 5 of 02-VERIFICATION.md (review CR-200, CR-201, WR-200): a hook in the cache checkout can publish bytes nothing read, a token nothing scanned, a push that reports success without the validated file, and a tree nobody can clone.

This is the fourth round of closing hook channels one at a time. So this plan stops listing what a hook may do to the tree after staging, and binds the commit to the tree UDE staged: one comparison refuses all of it. The reason the plan keeps per-file validation too is a counterexample probed at plan time: a post-index-change hook runs during `git add`, before the id is recorded, and can put a three-entry tree into the id itself. So the gate also reads that tree properly: each listed blob by its own object id, every validated path checked against its record, and the raw listing checked for repeated paths and bad path components.

Purpose: a push that returns Ok has published the recorded content at every validated path and no blob the gate did not read, whatever ran in the cache checkout. This plan does not validate file modes: a mode set before the tree id is recorded reaches the remote, and whether that is acceptable is the operator's question (T-02-60), which this plan does not answer.

Output: in src/sync/mod.rs, the staged-tree binding (StagedPublication, record_staged_tree, raw_commit_tree), blobs read by object id (raw_diff_entries, read_blob_by_id), the listing checks (tree_listing_blobs), the held-content check, name-free refusals, hook tests in both modes through push_to_remote, and direct-call and pure tests.

Plain git, does `git write-tree` agree with the tree `git commit` then writes? Yes in every case tried, one run each: normal edit; deletion through `git add` of a removed path; CRLF working file with a `text` attribute; rewriting clean filter (the id holds the filter's bytes, so the id alone does not catch it); pass-through filter; `git checkout -b` between `git add` and `git commit` (id unchanged); content-kept amend in a post-commit hook. Plain git, the counterexample: post-index-change hook, guarded so it acts once something is staged, running `git read-tree` of a tree listing V, I, V (validated, injected, validated). `git diff --cached` lists `M`; `git show :<path>` returns V; the write-tree id equals the commit's tree; `git show <commit>:<path>` returns V; `diff-tree --raw -z` lists the three entries with their ids (M with V's id, A with I's id, A with V's id); a plain push exits 0 and the remote holds I; a fresh clone's status shows the file deleted from the index. With the two-entry V, I tree instead, `git show :<path>` returned I (last entry wins in the index), so the staged gate catches it. The hook fired on `git status` (0 0), `git add` and `git write-tree`, and not on `git commit`, in a log-only run; `git read-tree` of a tree with a `.` entry is what `git clone` refuses, so `.` was not reached through the index by this route. A hand-crafted binary index was not tried.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Hooks that run after the tree is recorded (post-checkout in PR mode, prepare-commit-msg, post-commit, a process they left) -> the commit UDE pushes | They can rebuild the commit with any tree |

## Decisions and assumptions recorded here

- **Estimate basis (planner, 2026-11-01):** chars/4 over what the executor touches: this plan, PROJECT.md, STATE.md, 02-VERIFICATION.md, execute-plan.md and the summary template (measured sizes); symbol-scoped reads of src/sync/mod.rs instead of the whole file; about 40 KB of test and gate code per task; test and compiler output. `tokens` is that raw figure times the calibration factor 0.5 (`estimate-calibration`, 11 samples, clamped). It no longer assumes a whole-file read of src/sync/mod.rs, which alone would exceed it.
- **Binding adopted, with a correction to the idea as proposed (planner, evidence above).** The orchestrator asked to weigh binding the tree id against closing channels one at a time. Adopted, because after the id is recorded it refuses every tree change with one comparison, including ones nobody listed, and no legitimate state probed made `git write-tree` disagree with `git commit` or fail. The correction: it does not make per-file reads optional. Two reasons, both probed: the id holds a clean filter's bytes, and a post-index-change hook can put a three-entry tree into the id before it is recorded. So the listing checks and the by-id reads stay, applied to the tree that is bound. Binding removes the need to enumerate what a hook does after staging; it does not remove what the tree must contain.
- **Why binding alone is not enough (probed on git 2.56.0):** a post-index-change hook runs during `git add` (`--no-verify` does not skip it), and `git read-tree` of a tree listing the validated blob, the injected blob and the validated blob again leaves a primed cache tree, so the staged gate reads the validated bytes, `git write-tree` and `git commit` both return that tree, the recorded id equals the commit's tree, a read by path returns the validated bytes, and a plain push delivers the injected blob. So the gate also validates the content of that tree, read by object id.
- **A legitimate deletion has no record (read from the code at plan time):** push_updates records a digest only for files it writes (validated_blobs.record, src/sync/mod.rs:1642) and appends deleted templates to staged_files without a record (src/sync/mod.rs:1707). That is why the held-content loop cannot refuse it.
- **What this does not bind:** what `git push` sends outside the commit. There is no id to compare for an object walk, so grafts, commit-graphs, bitmaps, replace refs and shallow stay a list of channels (plan 02-12, plan 02-14). The verifier's warning that such a list is not proven complete still applies there. An option considered and not planned, reasoned and not probed: pushing from a scratch repository holding only the validated commit's objects would remove the checkout's hook-writable state from the walk. It would change how every user's pre-push hooks and credentials behave, which the operator has already declined for `--no-verify`. Raised in the handback.
- **Record location (planner):** in stage_publication, not immediately before `git commit`, so it is one site for both modes and a PR-mode post-checkout hook cannot move it. In direct mode nothing runs between the two.
- **Binding runs last (planner):** every other check reports first, so a refusal names the most specific cause, existing tests keep their messages (only the two name assertions change), and each check stays testable. Order has no effect on what publishes: all must pass.
- **No separate `D` refusal (planner, against the review's sketch):** the held-content loop covers deletion and revert with one check, and an explicit refusal would block the repair push when a fetched head already lists the managed file twice.
- **IN-205's committed-gate half folded in, because gap 1's property ("refusals never print the hook-chosen name") needs those two lines.** WR-201, WR-202, WR-204, IN-200..IN-204 and the older open findings stay out of scope; WR-201's rollback bug remains, and the token tests' roll-back assertion passes because those hooks keep the fetched head as parent.
- **Plan 02-11's decisions stand, with one open:** hooks are not disabled (approach B rejected) and the pushed refspec names the validated id. Its decision that file modes are out of scope was the orchestrator's (2026-10-28); the operator had not ruled on it when this was planned, and it is what T-02-60 asks.
- **Probe limits:** one run per mode and hook on git 2.56.0 on Linux, local bare remotes, in a scratch prototype whose test bodies are close to but not the ones this plan asks for. No hosted remote was tried. Whether a hosted remote's own fsck refuses these trees was not tested and is not relied on.
- **Windows:** `git_path_bytes` joins components with `/`, and raw `diff-tree` paths stay `/`-separated; not run on Windows (backlog Phase 999.1). Comparing the allowlist as raw bytes was rejected partly for this reason: PathBuf equality is kept and the component check does the rest.
