    GREEN, the fix:
    - `struct TreeEntry<'a> { mode: u32, name: &'a [u8], id: &'a [u8] }` and `fn parse_tree_object(bytes: &[u8], id_len: usize) -> Option<Vec<TreeEntry<'_>>>`, decoding entries as git's tree decoder does. Each entry is one or more ASCII octal digits, a space, a non-empty name of any other bytes, NUL, then exactly id_len raw id bytes. It gives None where git's decoder refuses: no digit, a digit outside 0-7, an empty name, no NUL, too few id bytes. It also gives None for a mode that overflows u32, which git's mode parser accepts by wrapping; there this decoder fails closed and does not match git. Empty input gives an empty list. The mode is kept canonical as git's canon_mode makes it: a regular file is 0o100755 when the owner-execute bit is set and 0o100644 otherwise, a symlink 0o120000, a directory 0o040000, anything else 0o160000.
    - `enum ListingDefect { Unreadable, Unparseable, IdMismatch(Vec<u8>) }`, a doc line on each variant. IdMismatch holds the listing path of the tree whose bytes do not hash to its id, empty for the root.
    - `fn verified_tree_listing(&self, repo: &Path, root: &str, verified: &mut HashMap<String, Vec<u8>>) -> Result<Vec<u8>, ListingDefect>`. The id length is root.len() / 2 for a 40- or 64-hex root, otherwise Unreadable. Each tree's bytes come from `verified`, or else from read_verified_object(repo, id, "tree") and are then kept in `verified` by id: IdMismatch gives IdMismatch(that tree's path) and Unreadable gives Unreadable; parse_tree_object's None gives Unparseable. ## Decisions and assumptions recorded here

- **WR-500 fix route (planner): build each route's listing in process from hashed tree bytes, in git's own listing format.** Every decision then comes from bytes that were hashed: blob ids, modes, deleted paths, and also repeated paths, bad components and empty directories. The existing parsers (tree_listing_blobs, count_empty_directories, the `listed` closure) and their refusal texts run unchanged on the same format, and the equivalence test can compare bytes with git's own output.
  - The reviewer's route, a walk along each recorded or deleted path only, is cheaper, but it leaves the structural checks on git's unchecked listing. A new tree holding a repeated entry could then be hidden from the listing and put back before the push, which sends it.
  - Keeping git's listing and checking each tree in a second read is WR-500 itself.
  - No git option was found that checks a subtree's bytes in the same read that produces the listing. `cat-file`, `ls-tree` and `diff-tree` do not check subtrees (02-22's measurements); a separate verifying command would again be a second read.
- **The commit too (planner).** Once git's listing no longer reads the commit on the committed route, nothing makes git check its id (T-02-100), so the commit is read through the same check. On the empty-status route the commit read is defence in depth: `rev-parse --verify` refuses a rewritten commit first.
- **Refusal texts (planner's discretion).** An id mismatch in a listing keeps 02-22's text, `an object read for {path} ...`, naming the first recorded, staged or allowlisted path under the mismatched tree, so 02-22's rows keep their assertions. With no such path the text names none. A tree path read from tree bytes is never printed (DEF-14).
- **The seam (planner, as the operator suggested).** A cfg(test) hook runs right after each route's listing read and puts the honest bytes back, so the swap is deterministic, with no racing process. At e39e860 it reproduces WR-500's false Ok through the engine. After the fix the listing itself refuses, because the forged bytes are hashed in the read the decisions come from. The hook is absent from non-test builds.
- **The per-task RED-commit gate (planner, after the plan checker).** It cannot see a RED commit that touches only src/*.rs (tdd.md, `Known gap — Rust (#4379)`; measured on 02-11, 02-12, 02-13 and 02-22). The RED rows cannot move to tests/: an integration test there builds the crate without cfg(test), so it has neither the listing hook nor the private helpers of src/sync/mod.rs. So a trip that the gap explains is recorded with substitute evidence that already exists (the RED commit by subject, the records), and a trip without it halts. Task 3 is test-only and carries no `tdd` attribute.
- **RED-commit scheme (operator rule after 02-22).** Rows committed ignored after a recorded failing run, then un-ignored with the fix. This gives test-before-feat order without committing a red suite.
- **WR-501 (planner).** Both: the two push rows now discriminate where they are refused (git status), and a direct test pins the gate's own root check with a same-bytes-own-id control. DEF-12's wording changes in plan 02-26.
- **WR-502 (planner).** `sleep 10` keeps the mutant's run under the 300 s bound while still overrunning the 2.5 s limit; 4 MiB is more than a pipe buffer holds.
- **IN-501 not taken (operator: only if cheap).** Telling a type mismatch, which is "not held", from a failed read needs ObjectDefect split. That changes texts DEF-11's rows pin, such as the tag-object row asserting `does not hold the validated content`. The two ancestor-tree sites the review names disappear with the code Task 1 and Task 2 remove; the blob-read site stays as the review describes.
- **Cost (reasoned; measured in the SUMMARY).** Each tree costs three git runs, each at least one 10 ms poll interval. A template repository like this project's has 15 trees, so about 45 runs per listing. Before, there was one listing run plus three runs per ancestor tree. Trees are hashed once per id per call. The SUMMARY records the module run's wall time before and after.
