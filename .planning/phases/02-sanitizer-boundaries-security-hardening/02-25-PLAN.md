<objective>
Close the base-side DEF-09 channel that 02-22-PLAN.md's `Not in this plan` bullet left with the operator, as the operator answered on 2026-11-04: `Plan 02-24: both`.

A fetched-head tree in the cache checkout whose stored bytes do not match its id can list an added file at the same blob id the commit holds. Then both the staged diff and `diff-tree` see no change there. The added path is never checked against the allowlist, and the commit publishes it. Measured with plain git at planning (below), the push succeeds and the remote lists the unvalidated path, with a blob the remote already held.

The committed gate is the binding check, so the fix goes there. Its change list is computed in process by listing_diff, from the verified listings plan 02-24 builds for the fetched head and the commit, in the exact raw format `diff-tree` prints. A rewritten fetched-head tree is then refused when it is read, and the change loop, its refusals and its parser run unchanged.

Output: listing_diff; validate_committed_tree reads the fetched head's commit and tree through the id check and no longer runs `diff-tree`; RED rows in both modes plus a function-level row; the equivalence tests. The closed-list rows, the controls on the final code and the phase gates are plan 02-26.
</objective>

## Decisions and assumptions recorded here

- **Fix route (planner): the committed gate computes its change list in process from two verified listings, in git's raw diff format.**
  - The committed gate is the binding check: the review's table classifies the staged gate's reads as not binding, so the fix goes where a refusal stops the push.
  - Checking the fetched head's trees in a second read and keeping `diff-tree` would repeat WR-500's flaw: a tree swapped back between the two reads would hide the path again.
  - Emitting diff-tree's own raw format keeps raw_diff_entries, the change loop, its refusal texts and DEF-10's parser tests unchanged, and lets the equivalence test compare bytes with git.
  - The fetched head's listing shares the commit listing's map, so only the fetched head's trees that differ from the commit's cost reads. That is the same set of trees `diff-tree` itself reads.
  - Measured above: sorting by path bytes is diff-tree's order, and a non-tree type change is `T`.
- **A repeated path (planner).** Records are matched as a multiset per path. A repeated commit entry that the base does not hold identically is listed as a change, as git's own merge walk lists it, so the change loop still reads and scans it.
- **`pack.window 0` in the push rows (planner, measured).** It makes the RED's false Ok deterministic. At planning the one-file fixture published with and without it; 02-22's probe saw `unpacker error` without it.
- **The empty-name row (planner).** The commit's listing now refuses an empty entry name, as git's tree decoder does, before any change is listed; the refusal text changes from `git diff-tree failed` to `unparseable tree entry`, the outcome (refused) does not.
- **The `.` and `..` rows (reasoned).** listing_diff lists `templates/./f` and `templates/../f` exactly as diff-tree did, so these rows keep their texts.
- **Flagged assumptions (spec-less fallback).** As in 02-24: SEC-01 unclassified, SEC-02 unclassified, SEC-03 `empty` and SEC-03 `encoding` are carried and owned by plans 02-01 to 02-10; src/sanitizer and src/template unchanged (Task 2's gate); SEC-04 `boundary` and `precision` are truths here.
