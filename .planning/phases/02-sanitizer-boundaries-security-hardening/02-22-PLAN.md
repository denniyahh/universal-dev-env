Both routes decide "held" from bytes in the cache checkout's object store. git returns the bytes stored under an id without checking that they hash to it, both for a blob read with `cat-file` and for a subtree walked by `ls-tree -r` (measured below). So a blob or tree the remote already holds can be rewritten locally and read as the record. The result is Ok on the committed route (DEF-11) and on the empty-status route (DEF-12), and direct mode records an ancestor for content the remote does not hold.

Purpose: before a blob, or a tree above a recorded or deleted path, counts for either route, it is hashed with git's own hash and compared with its id. Ok then means what promise 2 of docs/ARCHITECTURE.md says.

## Decisions and assumptions recorded here

- **Fix route (planner): (a), re-hash what the checks read, through git.** Both gaps go through one read, read_blob_by_id inside first_path_not_held, which both routes call, so one check covers both.
  - Route (b) does not close the gap. It would record each validated file's blob id at staging and require the tree to list that id. But the id taken from the index is itself read by id from the same store, and a rewritten subtree lists the recorded id while the remote's subtree lists the seed's (measured: `ls-tree -r` exit 0 with the validated id at the path).
  - The hash is git's. `git hash-object` run in the checkout uses the repository's own object format (SHA-1 or SHA-256, measured). The project has `sha2` and no SHA-1 crate, so hashing in process would add a dependency and a supply-chain checkpoint. `--literally` keeps the check to hashing, with no format check that could refuse a legitimate tree, and stdin with `--no-filters` hashes the bytes exactly.
- **Trees too (planner, beyond the verifier's `missing` lines, within its gap text "a local object whose bytes do not match its id").** The review reasoned the tree variant; it was measured here for subtrees. A blob-only fix would leave a rewritten subtree giving Ok on both routes and hiding a deleted path. The root tree and the commit are checked by git (measured), so they get pin rows, not code.
- **Stdin for the hash (planner).** Production commands bind stdin to the null device. A writer thread is the smallest change that feeds bytes without writing them to a temporary file.
- **A refusal text of its own (planner's discretion).** Genuine disk corruption also lands here, and `does not hold the validated content` would then send the user looking for a hook that hid their change. A distinct text also lets every row tell the id check from the content check, which the controls rely on.
- **Cache-tree priming in the tree rows (planner, measured).** After a fresh clone and reset, a rewritten subtree shows as a staged modification and the staged gate refuses first. `git write-tree` primes the cache-tree, which a hook can do; then only the gate's listing sees the tree.
- **Cost (reasoned).** Each blob the gate reads costs one more git run, and each distinct tree above a recorded or deleted path costs three. Each run is roughly 10 ms or more, because of POLL_INTERVAL. Trees are checked once per id per call.
- **Not in this plan; put to the operator by the orchestrator (planner's probe, plain git, 2026-11-04).** A base-side tree whose stored bytes do not match its id can hide an added file from the staged diff and from `diff-tree`. The forged base tree listed the added entry, so both comparisons saw no change. The commit's own listing then carries the unrecorded path.

  - Not run through UDE. It fits DEF-09's channel, "an added file", not DEF-11 or DEF-12, so it is outside the scope the operator set. read_verified_object would be the check to apply to those base-side reads.
