- `process_wrap::std::CommandWrap::from(std::process::Command)`; `.wrap(process_wrap::std::ProcessGroup::leader())` on Unix; `.wrap(process_wrap::std::JobObject)` on Windows; `.spawn() -> std::io::Result<Box<dyn process_wrap::std::ChildWrapper>>`.
- `ChildWrapper`: `stdout(&mut self) -> &mut Option<ChildStdout>`, `stderr(..)`, `id()`, `start_kill() -> io::Result<()>` (Unix: killpg(pgid, SIGKILL)), `try_wait() -> io::Result<Option<ExitStatus>>`, `wait() -> io::Result<ExitStatus>` (waits for the leader, then waitpid(-pgid) until ECHILD).
- No blocking wait-with-timeout and no kill-on-drop for std: poll `try_wait` and kill explicitly on every exit path.
- `try_wait` only reaps direct children; grandchildren reparented away are never returned, so a leader exit is observed even while grandchildren still run.
- `start_kill` is `killpg(pgid, SIGKILL)` on the leader's group only (verified in process-wrap 10.0.1 src/std/process_group.rs, `signal_imp`). A descendant that called setsid is in another group and is NOT reached, so it can keep the stdout/stderr pipes open after the kill. Once every group member has exited, killpg fails with ESRCH (measured at plan time with `/usr/bin/kill -KILL -- -<pgid>`: "No such process").

Measured at plan time on this host (bash probe, sh made a group leader with setpgrp to mirror ProcessGroup::leader): `sh -c 'setsid sleep 6 & echo $! > "$1"' sh <file>` writes the PID of the outside holder itself (util-linux setsid does not fork when its caller is not a group leader; /proc/<pid>/comm is `sleep`, and its PGID and SID equal its own PID); a kill of the original group leaves it alive; `/usr/bin/kill -KILL -- -<holder pgid>` kills it. setsid comes from util-linux; find it with `which::which("setsid")` (the `which` crate is already a dependency), never by a hard-coded path (on this host it is /home/linuxbrew/.linuxbrew/bin/setsid and /usr/bin/setsid).

    run_bounded algorithm: call prepare_command; wrap in CommandWrap with ProcessGroup::leader() under cfg(unix) and JobObject under cfg(windows); spawn, mapping failure to `Failed to spawn {label}: {e}`; take the stdout and stderr pipes and read each to end on its own std::thread; compute the deadline from Instant::now() + timeout; loop on try_wait, sleeping POLL_INTERVAL between polls. Bounded-join rule, applied on every path: a reader JoinHandle is joined only after JoinHandle::is_finished returns true, never blindly. Factor this into one private helper (for example `fn join_readers_by(stdout, stderr, limit: Instant) -> Result<Option<(Vec<u8>, Vec<u8>)>, String>` returning None when the limit passes first) so each path stays short. When the limit passes with a reader still blocked, drop its JoinHandle: the thread is detached and exits by itself once the last pipe holder closes; run_bounded does not wait for it.

    On Ok(Some(status)) the leader has exited: poll the readers until the same deadline; if both finish, return Ok(RunOutput). Otherwise call start_kill (group) and ignore its io::Result (it fails with ESRCH when no group member is left), then poll the readers for up to KILL_GRACE; if both finish, return Ok(RunOutput); if not, a descendant outside the group (setsid) still holds the pipes: detach the readers and return Err `{label}: output pipes still held open {grace:.1}s after its process group was killed (a descendant left the process group); output discarded` with grace = KILL_GRACE.as_secs_f64(). Rationale for not killing the group unconditionally after a normal exit: a credential-cache daemon started by git stays in the group but closes the inherited stderr, and killing it would drop the user's cached credentials on every call [ASSUMED from git's credential-cache--daemon behaviour; the runner behaviour itself is proven by test_background_process_without_pipes_survives]. On deadline with the leader still running: start_kill, then wait (reaps the leader and group members; it does not wait for processes outside the group), poll the readers for up to KILL_GRACE and detach them if they are still blocked, and return Err with the exact form `{label} timed out after {secs:.1}s and was terminated (UDE runs git/gh non-interactively: cache your credentials or load your SSH key into ssh-agent)` where secs is timeout.as_secs_f64() (Pitfall 6 hint), whether or not the readers finished. On try_wait Err: start_kill, wait, the same KILL_GRACE-bounded reader poll, return Err `{label}: failed to wait for child: {e}`. A reader thread that panicked maps to Err `{label}: output reader panicked`. Never format the argv into any message (Pitfall 9). Worst-case return time is therefore timeout + KILL_GRACE + the group wait, regardless of what descendants do.

## Decisions and assumptions recorded here

- D-03 implemented as specified (process-wrap 10.x, group kill).
- Discretion (timeouts): tiers 30 s local / 60 s network as named constants; the timeout is a function parameter so tests pass 300 ms. This is internal parameterisation, not the deferred user-facing override.
- Planner decision (inside Claude's Discretion): after a normal leader exit the runner waits for the pipes until the deadline instead of killing the group at once, so background helpers that close inherited pipes (credential-cache daemon) survive. Research Pattern 1 proposed an unconditional post-exit group kill; this plan deviates for the credential-cache reason and keeps the bound.
- Planner decision (revision 2, checker finding on unbounded joins): the group kill cannot reach a descendant that called setsid, so the bound comes from the join, not the kill. Readers get KILL_GRACE (1 s) after the kill and are then detached; a detached thread exits on its own when the outside holder closes the pipe. Accepted cost: on that rare path the output is discarded and the call returns Err, and one blocked thread per event lives until the holder exits; for an on-demand CLI this is bounded by process lifetime. git's own daemonizing children (gc --auto, research Assumption A2) are expected to close their standard streams when they daemonize, so they should not trigger this path [ASSUMED from git's daemonize() closing fds 0-2; not probed at plan time; if one does, the effect is an Err after timeout + KILL_GRACE, never a hang].
- Revision 2026-10-18 (external review, timing headroom): every wall-clock bound now sits at least 2 s below the broken case and at least 2 s above the expected correct run, so a loaded build host does not fail a correct implementation (test_timeout_kills_group < 3 s; background test 2 s / 3 s with a 6 s sleep; pipe-holder tests < 5 s). While re-deriving the bounds, test_timeout_kills_group turned out not to discriminate on time alone: with the KILL_GRACE-bounded join from revision 2, a leader-only kill also returns the timeout Err in about 1.3 s. It now records the background grandchild's PID and asserts that it is dead, which is the real group-kill check, and it moves to the Linux gate because it reads /proc. The setsid-missing-panics design is unchanged.
- Coupling with plan 01-02 is declared in `coupling_justified` (frontmatter): no shared files; only the shared build matters, and only in a shared working tree.
- Assumption A1 (research): an ssh passphrase prompt in a background process group gets SIGTTIN and times out rather than prompting; the timeout message carries the ssh-agent hint either way.
- Edge probe (spec-less fallback): SYNC-03 empty and ordering lifted as explicit truths, adjacency as a backstop truth.
